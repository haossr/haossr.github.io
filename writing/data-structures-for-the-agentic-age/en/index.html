The Data Structures of Human Attention in the Agentic Age

From fitting machines to organizing human attention

TL;DR: Human-facing data structures for the agentic age should be organized around human attention. Calendar allocates finite attention across time; Thread lets work pause and resume without losing its history; Filesystem lets attention move between concrete objects and layers of abstraction. These are not three isolated products, but three directions in which the same attention moves.

This essay is itself an example. In Calendar, it is a block of time that cannot be spent twice; in a Thread, a history that can be paused and resumed; in a Filesystem, a state tree that can be traversed from the whole project down to a single sentence. It is one piece of work, yet it has three identities in three systems.

This is the data-structure problem of the agentic age. Arrays, hash tables, and B-trees are not going away. What changes is that agents increasingly take over the low-level translation work. The structures people face directly should optimize for a different set of costs: collisions in attention, context recovery, collaborative handoffs, and trust in actions.

Calendar, Thread, and a versioned Filesystem are not, of course, one category of textbook data structures. A more precise name might be “human-facing coordination primitives.” I still want to call them data structures because they determine where human attention can move: scheduling into the future, carrying history forward, and zooming across levels of abstraction. Buttons are the interface. These rules are the product's skeleton.

1. From Machine Data Structures to Human Data Structures

From the beginnings of modern computer science, data structures and algorithms have been among its most durable foundations. We learn arrays, linked lists, trees, hash tables, and graphs; we learn how to make search, insertion, and deletion faster. But a data structure is never neutral. It writes the costs a system most wants to reduce into its default operations.

The history of computing is not a straight line in which high-level structures replace low-level ones. A better account is that new constraints first enter the structure, then a higher layer of abstraction hides some of that complexity from people. The abstraction boundary keeps moving upward, but the layer below never disappears.

Early arrays were nearly a projection of contiguous memory. The 1957 paper describing the FORTRAN system showed programmers writing array subscripts and mathematical-looking expressions, while the compiler generated address calculations and machine instructions for the IBM 704. It did not eliminate machine code. It transferred a great deal of address calculation and instruction selection to the compiler.[1]

The B-tree is a classic example in the other direction. It does not move away from hardware; it understands the hardware more deeply. Nodes are designed around fixed-size disk pages, the branching factor depends on the device, and the dominant cost of a lookup is not the number of comparisons but the number of pages fetched from external storage. The shape of a B-tree carries the rhythm of the disk.[2]

In 1970, E. F. Codd's relational model pushed the abstraction boundary upward again. He made the requirement explicit: database users should not need to know how data is organized inside the machine, and a change in the underlying representation should not force end users or most applications to be rewritten.[3] From that point on, “what relationships do I want?” could be more stable than “which pointer do I follow?” Under a relation there might still be a B-tree, a hash index, or some other structure, but choosing and maintaining it increasingly became the database system's responsibility.

By the time of Smalltalk, this trajectory had clearly moved from the machine toward the human conceptual world. In 1981, Daniel Ingalls argued that a computing model should fit the human mind, not the other way around. He offered a useful example: a music system can certainly store a melody as a sequence of integers encoding pitch and duration. But if the language gives Note, Melody, and Score the same standing as integers, people will naturally think about music in notes rather than numbers.[4]

Arrays, B-trees, the relational model, and Smalltalk objects may seem far apart, but they share one trajectory: whenever the abstraction boundary moves upward, the lower layer remains, while translation work shifts from the person to the system. The agentic age moves that boundary up once more. The machine side still optimizes memory, I/O, and query plans; the human side should optimize switching, recovery, handoffs, and authorization. The agent's job is to translate continuously between these two cost models.

The new source language is the human workflow. The compiled output is no longer just code, but a sequence of real-world actions that can be inspected and undone.

“Preference” here does not mean a theme color. It means operating rules: when a person can focus, how they recover from interruption, how finely they tend to divide projects, which actions may run automatically, and which require approval. As early as 1962, Douglas Engelbart argued that the person and the tools that augment the person's capabilities should be designed as a single system.[5] Agents make it possible for these rules to become first-class system inputs.

2. Three Directions of Attention

Calendar, Thread, and Filesystem are more than three containers for things. They move attention in three directions: Calendar schedules it into the future, Thread carries the past forward, and Filesystem lets it zoom between detail and the whole. These directions are not orthogonal. Their overlaps are where real work happens.

Calendar
Time axis: Finite Attention

The core of Calendar is not dates but exclusivity: at a given moment, a person's critical attention cannot be fully occupied by two complex tasks. Calendar projects goals and commitments onto a finite set of potentially conflicting intervals. Its basic unit is not an abstract “to do,” but a claim on a span of time that cannot be reused. In iCalendar, a VEVENT expresses its start with DTSTART and may express its end or duration with DTEND or DURATION; it can also carry recurrence rules and attendees. Busy-time semantics are expressed through event transparency and components such as VFREEBUSY. Time is not a label. It is a constraint.[6]

For complex tasks that demand central decision-making, working memory, or rule control, one useful design approximation is that critical cognitive steps encounter a serial bottleneck. We can switch between tasks, and highly automated activities can partially overlap, but complex tasks still compete for finite cognitive resources. Herbert Simon famously described an abundance of information as producing a scarcity of attention; later task-switching experiments have repeatedly found switching-time costs, which generally rise with the complexity of the rules involved.[7][8]

This does not require us to pretend that the brain is strictly single-threaded. It is enough to acknowledge that complex work shares limited cognitive resources and that switching has a cost. Calendar's role then becomes clear: it does not eliminate that cost, but makes it visible. Suppose Monday from 9 to 11 is reserved for this essay. That is not merely a reminder to “write”; it is a two-hour commitment of attention. Put a meeting at 10, and a vague priority conflict immediately becomes a visible overlap between intervals.

A to-do list is a wish list; Calendar is an attention budget. A budget is not the same as actual spending—meetings get canceled and plans fall apart—but it at least forces every priority to occupy some finite span of time. A long-range planning agent should not merely add more tasks to an inbox. It should compare goals, scheduled time, and actual investment.

Thread
History axis: Context Continuity

The core of Thread is not message order but context continuity. It lets attention leave, stages unfinished goals, decisions, questions, and artifacts, and then lets the same person, another person, or an agent continue along the same history. A Thread need not be an immutable, append-only system log. More precisely, its default is to preserve the path of the work rather than show only the latest state.

Session and Thread are often used interchangeably. Here I treat them as two layers. A Session is one continuous stretch of work with a beginning and an end. A Thread is the persistent semantic container that recognizes many pauses, resumptions, and handoffs as “the same thing.”

Spend 15 minutes outlining today, two hours researching tomorrow, 30 minutes discussing the title the day after, then return a week later to revise the ending. Calendar sees four separate spans of time. Thread sees one intent that is still developing. Time is discontinuous; meaning is continuous.

An email Thread need not be a straight line either. The REFERENCES algorithm in RFC 5256 uses Message-ID, References, and In-Reply-To to reconstruct parent-child relationships, then uses subject rules to merge related roots. The result is closer to a reply tree than a linear sequence.[9] Earlier prototypes for activity-centric collaboration went further, placing messages, chat transcripts, files, folders, tasks, and screenshots into a single persistent Thread so that synchronous and asynchronous collaboration could share one line of work.[10]

But a reply relationship is not automatically a semantic relationship. An email reply may have changed the subject entirely, and one chat window may contain three different pieces of work. An agentic Thread therefore cannot be just a word-for-word transcript. At minimum, it must preserve the goal, key decisions, open questions, participants, related artifacts, and “whose turn is next.”

A Session is a slice of time in which work happens. A Thread is the unit through which work can be recovered and handed off.

This makes Thread a natural structure for collaboration. People and agents need not be online at the same time, nor replay every prior Session. On entering a Thread, either should be able to answer quickly: Why are we doing this? What have we tried? What do we currently believe? What comes next?

Versioned Filesystem
Hierarchy axis: Hierarchical Abstraction

The core of Filesystem is not merely storing files but providing hierarchical abstraction. Opening a file moves toward the concrete; backing out to a directory, a project, or an entire workspace moves toward the abstract. Writing a document, building slides, analyzing data, changing code, preparing visa materials, or completing due diligence on a house all require movement in both directions: Which object am I looking at now, and what larger whole does it belong to?

A hierarchical filesystem decomposes complex work spatially through tree-shaped paths. The classic Unix design put ordinary files, directories, and special files into one hierarchical naming system. A path is both a locator and a decomposition from coarse to fine. Because an ordinary file can appear in more than one directory through hard links, the underlying structure is not strictly a tree—but a tree remains the primary interface presented to people.[11]

This interface is not merely an inferior substitute for search. In a personal-information-management study with only 14 participants, 13 were unwilling to give up folders even when researchers posited a fast, private search tool that required almost no maintenance. Directories also helped them understand relationships, see the shape of a project, and notice unfinished parts.[12] Such a small sample is no universal law, but it gives a concrete account of the cognitive value of a tree beyond retrieval.

An ordinary filesystem mainly exposes the current mutable state. Git connects successive directory trees through time. A commit points to the top-level tree that recursively describes a project snapshot and records parent commits, author, time, and message. A branch is a movable reference to a commit, and a merge commit may have multiple parents. History is therefore a directed acyclic graph, not a linear backup.[13]

A versioned workspace therefore answers three kinds of question at once: What exists now? How did it become this way? If this direction is wrong, can we return to an earlier state or start a new line of work from it? The faster agents make changes, the less we can treat diffs, provenance, and rollback as mere engineering details. They become trust interfaces.

File trees have limits as well. Traditional hierarchies are good at expressing containment and decomposition, but poor at expressing that one object serves several projects at once. When Vannevar Bush imagined the Memex in 1945, he criticized retrieval systems that forced people down a single path through a hierarchy and proposed named, shareable associative trails instead.[14] The workspace of the future therefore needs a tree as its skeleton, but also links, tags, and semantic edges as lateral connections.

Taken together, the division of labor is clear: Calendar manages finite capacity, Thread preserves context continuity, and a versioned workspace provides hierarchical abstraction and recoverable state. Calendar answers “when is attention exclusively committed here?” Thread answers “which history does it carry forward?” Filesystem answers “which layer of state is it observing or changing?”

3. The Intersections Matter More Than the Circles

The point of the diagram is not the three independent regions, but the pairwise overlaps. Each intersection identifies the default semantics shared by two structures, while also clarifying what makes the third different.

Calendar × Thread
Unfolds Over Time

Both make sequence, intervals, and duration meaningful. Calendar unfolds work into multiple Sessions; Thread gathers those separated slices of time back into a continuous history. Filesystem, by default, first presents a state snapshot at a particular moment.

Calendar × Filesystem
Mutable State

Move an event, edit a file, or rename it, and the interface directly presents a new current state. Thread has a different default emphasis: it preserves the process so that the next step can build on the existing history, rather than simply overwrite it with a new state.

Thread × Filesystem
Parallel Contexts

Many Threads, directories, branches, and worktrees can coexist and fork without inherently conflicting. A person's Calendar, however, remains bounded by finite attention. Multiple agents can advance separate contexts in parallel, but a person's critical attention at a given moment cannot be copied.

Attention sits at the center: which span of time holds it now, which history does it carry forward, and which layer of state is it observing or changing?

This also explains why unification cannot mean erasing the differences. Calendar should continue to expose conflicts. Thread should continue to preserve the path by which work arrived here. Filesystem should continue to let us drill from the whole into the details. The opportunity is not to invent a universal container, but to keep these three semantics aligned around the same piece of work.

4. Unifying Them Is the Product Opportunity of the Agentic Age

The problem is that these three structures remain deeply fragmented today.

Return to the essay at the beginning. The three systems are not incapable of referring to one another; what they lack is a shared identity for the work.

Putting a URL in each system is not unification. In fact, the iCalendar standard has long allowed events to carry attachments and URLs, and it uses RELATED-TO to express relationships among calendar objects.[6] What is missing is not another set of links, but shared identity and shared state semantics. Is this file pre-meeting material, a post-meeting artifact, or an obsolete draft? Which long-term goal does this follow-up belong to? Is this Thread active, waiting, or complete? Today these states are copied across products and quietly diverge.

True unification should let the same piece of work have three simultaneous projections: a commitment of time in Calendar, a history in Thread that can pause, fork, and be handed off, and a state in Filesystem that can be browsed, compared, and rolled back. The projections do not have to live in the same app, but they must share an identity and understand one another's state changes.

Those projections should also update in both directions. Click a writing block in Calendar, and an agent should restore the corresponding Thread, open the latest draft, and tell me where I stopped. Decide in the Thread to “cut Section 4,” and that decision should become a reviewable file change. Once a round of fact-checking lands as a Git commit, the Thread should gain a clear checkpoint. If the English edition is still missing, Calendar can suggest the next suitable block of time instead of turning it into another context-free reminder.

This does not mean cramming Calendar, chat, and a file manager into one super-app. A more promising direction is to give the same piece of work a stable identity, then let each structure present it differently. Call that identity a Work Object for now. It links the goal, the originating Thread, files and commits, human and agent participants, permissions, status and dependencies, scheduled time, and the log of real-world actions. It is not a fourth circle, let alone the conceptual center of this model. It is simply the primary key shared by the three projections.

Intent could be a field on the Work Object, or simply its product name. But the name matters less than the boundary. When does the object split or merge? Which context and permissions do subtasks inherit? When Calendar, Thread, and workspace disagree, which state has final authority? These rules determine whether the system is maintaining one piece of work or merely creating a fourth copy of state that can drift.

Existing systems are capable of storing these relationships. Their failure is that they require people to maintain them continuously: create a project, file an email, attach a document, update a status. An agent can shift this workflow from manual bookkeeping to exception handling. It can first propose which events, conversations, and commits belong to the same intent, asking for confirmation only when uncertainty or risk is high. It is not merely searching material that already exists; it is continuously maintaining referential integrity among that material. That is why unification has become a product opportunity now.

The key metrics should therefore extend beyond search latency. How long does it take to recover a piece of work? How many artifacts have lost their context? How far does planned attention diverge from actual investment? Can every agent action be traced to a goal, an authorization, and a specific diff?

Imagine preparing a talk. The first rehearsal is at 2 p.m. Open the calendar event, and the system restores the corresponding Thread, opens the latest slides, and highlights the argument left unresolved last time. Afterward, the recording, feedback, edits, and commit return to the same line of work. If another rehearsal is needed before the deadline, Calendar suggests the next block. To a person, this was always one thing. Only today's software split it into a meeting, a conversation, and a set of files.

Work Object is only the current working hypothesis. It may ultimately be called a Task, Goal, Project, or Intent. Whatever the name, it must define how to contain subtasks, dependencies, forks, and merges; where permissions and agent capabilities attach; which relationships may be established automatically and which require human confirmation; and how to resolve conflicts among Calendar, Thread, and workspace.

These are not implementation details. This minimal primitive will determine whether the product merely “connects three apps” or establishes a new human-agent operating system.

Conclusion

Traditional data structures write the machine's cost model into software: whether memory is contiguous, how much data moves in one I/O operation, how concurrency is coordinated. The agentic age does not cancel those constraints. It simply makes another set of costs worthy of becoming first-class concerns in product design: human attention, the time required to recover context, and trust in actions that change the real world.

For the next generation of personal computing, the point is not merely to make the machine another order of magnitude faster. It is to let one piece of work cross many days, many people, and many applications while remaining recoverable, ready to hand off, and verifiable. Calendar shows when attention is exclusively committed. Thread shows which history it carries forward. Filesystem shows which layer of state it is observing or changing. The real product opportunity of the agentic age is not to bolt three apps together, but to keep these three coordinates of attention aligned, recoverable, and verifiable.
